What is HSTS?

A response header that tells the browser to always connect to that domain over HTTPS.

strict-transport-security:
  max-age=31536000; includeSubDomains; preload

use https://hstspreload.org/ for validation and to register for preloading.

So I'll keep this short, since you here to learn about CSP. But since HSTS was the other half of getting to an A grade, I'm covering it.

This tells the browser never to use plain http for this domain again (or for as long as the max-age is set).

Everything about it is in that one header, which is why it takes five minutes and CSP takes a quarter.

Some other gotchyas though

It's improper to include this in a regular http response, even if you are redirecting to https

You shouldn't combine redirects for non-www and https. Redirect to https first, then issue a second redirect for www.

How can I set up HSTS?

In Drupal, the Security Kit module can do it. You can also set the header directly in PHP, or (better) at the web server / CDN layer.

Avoid slip when adding redirects

Preference order is web server or CDN first, then a module.

It's a static header that never changes, so there's no real reason for PHP to be generating it on every request.

Warning

Once a site sends HSTS, if you ever let the certificate expire, no one will be able to reach the site.

The failure mode here is total, which is why it gets its own slide.

Browsers remember the header for as long as you told them to. So if the certificate lapses, nobody can reach the site, and there is no way to reach out and tell them otherwise. Start with a short max-age and raise it once you trust your renewal process.

The default-src gotcha

A resource type is unrestricted when none of the directives in its fallback chain is present.

content-security-policy: script-src 'self';

Scripts — and workers via fallback — are restricted. Images, styles, fonts, frames and connections are not.

Spec: default-src · fallback list

This is the part people miss.

The precise rule is that the browser walks the fallback chain and uses the first directive it finds. Here, script-src also covers script elements, script attributes and workers. Resource types with no directive anywhere in their chain are not restricted by CSP.

The fallback trap

Fallbacks are not merged. The first directive present in the chain wins.

content-security-policy:
  child-src 'self' td.doubleclick.net;
  frame-src 'self';

frame-src governs frames, so the iframe is blocked. child-src is not consulted.

The console reports the block — not that child-src was shadowed.

Spec: fetch-directive fallback list

This is a real bug from a project I was on recently.

The browser reports an ordinary frame-src violation when the frame is attempted. It does not diagnose the configuration mistake: nothing says the source listed under child-src has stopped applying to frames.

…and the dead entry isn't inert

With frame-src present, child-src no longer governs frames. Without worker-src, it still governs workers.

worker-src → child-src → script-src → default-src

Removing child-src can therefore change worker behavior through the next fallback.

Spec: worker-src · fallback list

This matters while worker-src is absent. Removing child-src exposes the next worker fallback, so the result depends on script-src and then default-src. An explicit worker-src would shadow all three.

…except when they don't

Five directives do not fall back to default-src. Setting default-src 'self' gives you exactly nothing on any of them:

  • form-action — where forms may submit
  • base-uri — whether an injected <base> can reroute every relative URL
  • frame-ancestors — who may frame you
  • sandbox, upgrade-insecure-requests

They're navigation and document directives, not fetch directives. The fallback chain only exists inside the fetch family.

The other half of the rule I just taught.

These are navigation and document directives. The fallback chain only exists inside the fetch family, which is not obvious from any of the documentation.

Which means this policy…

content-security-policy: default-src 'self';

…will happily let an injected form post your users' data to my server. No violation. No console error.

object-src isn't just a Flash relic

Flash is why the directive exists. It is not why it's still in the recommended policy.

<object> and <embed> load documents that execute script — and script-src does not govern them. An HTML or SVG file on your own origin (a file upload, a webform attachment) becomes script execution that your script-src never sees.

object-src 'none';

The common assumption is that this one is dead weight now that Flash is gone.

It isn't. Object and embed load documents that run script, and script-src doesn't govern them. A file upload or a webform attachment is the realistic way somebody gets a file onto your origin.

Key features in CSP

The next few slides are the things you'll actually be typing into a config form.

Everything so far has been the model; this is the vocabulary.

'unsafe-inline'

content-security-policy: script-src 'self' 'unsafe-inline';

Allows inline scripts/styles. i.e. anything inside a <script> tag, or "onclick" handler.

Weak — but still better than no CSP at all as a starting point.

This is where most people start, and it's a reasonable first step.

It's also why a lot of policies score badly — people turn it on to stop the errors and then never come back to it.

Hashes

content-security-policy: script-src 'sha256-B2yPHKaXnvFWtRChIbabYmUBFZdVfKKXHbWtWidDVF8='

Allow-list a specific inline script or style by the base64-encoded SHA hash of its contents.

Note: adding any hash or nonce to script-src makes the browser ignore 'unsafe-inline' (a feature, not a bug).

MDN: script-src

Hash the contents of the block, put the hash in the header.

The detail worth pointing at is the last line. Adding any hash or nonce switches unsafe-inline off, whether you meant it to or not.

The hash gotcha

Plain hashes (and nonces) only apply to elements — <script> / <style> blocks.

They do not cover inline event handlers (onclick=) or inline style="" attributes…

Reference

This is the one that costs people an afternoon.

Hashes cover elements. They don't cover attributes, and the error message doesn't make that obvious.

'unsafe-hashes'

content-security-policy: script-src 'unsafe-hashes' 'sha256-...';

The CSP Level 3 keyword that lets a hash match an inline event handler or style attribute — the gap from the previous slide.

Still "unsafe" (less so than 'unsafe-inline'). The better fix is to remove inline handlers/attribute styles entirely.

content-security-policy.com/unsafe-hashes

This is the escape hatch for the previous slide.

Better than unsafe-inline, still not something to be happy about. Removing the inline handler is the actual fix.

Nonces

<script nonce="ABC123">…</script>
content-security-policy: script-src 'nonce-ABC123'

Allow-list inline code by an arbitrary, server-generated string. Generate a fresh nonce on every request.

MDN: script-src

A random value, regenerated on every request, matched between the header and the tag.

Don't use static nonces.

A nonce that never changes is just a password the attacker can read — it defeats the purpose.

This happens more than you would expect, usually when somebody hardcodes one to get past an error and it never gets changed back.

The modern recommendation: a "strict" CSP

Allow-listing host after host is brittle and often bypassable. Today's guidance (web.dev, Google) is a nonce + 'strict-dynamic' policy.

This is a genuine shift in guidance, not just a preference.

The host allow-list approach doesn't scale and it turns out to be bypassable more often than people assumed.

'strict-dynamic'

content-security-policy:
  script-src 'nonce-{random}' 'strict-dynamic' https: 'unsafe-inline';
  object-src 'none';
  base-uri 'none';

A nonce'd script may load further scripts, and trust is propagated to them — so you don't have to nonce or allow-list every third-party file. Older browsers ignore 'strict-dynamic' and fall back to the host list / 'unsafe-inline'.

Trust propagates from the nonced script to whatever it loads, so you stop maintaining a list of script hosts.

Worth flagging that this published recipe has no default-src. That's deliberate in the original — it's aimed squarely at XSS — but add one in production, for the reason two sections back.

Rule of thumb

  • Nonces when you can generate markup dynamically (most Drupal pages).
  • Hashes when the content is static / cached and you can't inject a per-request nonce.

Short answer for the question people are about to ask.

Trusted Types

A layer on top of CSP (require-trusted-types-for 'script') that locks down DOM-XSS sinks like innerHTML — forcing dangerous values through a named policy where you actually sanitize.

content-security-policy: require-trusted-types-for 'script'; trusted-types app-sanitizer;

No longer Chromium-only: Safari 26 (2025) and Firefox 148 (early 2026) added it, so it's now a cross-browser defense. It doesn't sanitize for you, and the cross-browser floor is recent — deploy report-only first.

This is a different kind of protection from the rest of the talk.

Everything else is about where things load from. This one constrains what your own code is allowed to do with an untrusted string.

On the horizon — don't ship these yet

CSP Level 3 is still a W3C Working Draft: it's the model browsers actually implement, but not a finished Recommendation, and it keeps gaining narrow features. Worth knowing, not yet baseline:

  • 'report-sha256' / 384 / 512 — script-inventory telemetry (browser reports a loaded script's hash); Chrome 133+. Not the same as allow-listing by hash.
  • 'trusted-types-eval' — a narrower alternative to 'unsafe-eval' when Trusted Types is active.
  • Chromium origin trial: URL hashes, eval hashes, 'strict-dynamic-url' — names look like standard hashes but aren't portable.
  • Embedded Enforcement (<iframe csp="…">) — a separate draft, not a replacement for frame-ancestors/sandbox.

Skim this one.

The point is just that the spec is still moving, so be careful about copying things you find in origin trials or recent blog posts.

Current limitations of CSP

Safari was historically buggy — much improved now, though still trails Chromium on the newest bits (e.g. Trusted Types).

Granular directive support is now broad, but not universal.

A weak CSP (lots of 'unsafe-inline' / wildcards) can still let attacks through —

and even a strong one can sometimes be circumvented.

Worth being honest about what it doesn't do.

A weak policy gives you the header and the passing grade without much of the protection.

Two worth knowing about.

Your header is not your config

The CSP module composes the header at request time from three sources:

  1. csp.settings — what you exported.
  2. Every *.libraries.yml in the codebase. LibraryPolicyBuilder scans external CSS/JS URLs and appends those hosts to script-src / style-src.
  3. Any module subscribing to CspEvents::POLICY_ALTER — e.g. Google Tag appends GA/GTM hosts to img-src and connect-src on its own.

On one site, cdn.jsdelivr.net, unpkg.com, cdnjs.cloudflare.com and use.fontawesome.com all appear in the live header and in zero lines of config. They come from contrib libraries — Webform, Font Awesome, Geofield Map.

This one surprises people, including me the first time.

The module assembles the header from three sources, and only one of them is the config you exported.

So curl -I is the only source of truth

Good news: the module does real work for you.

Bad news: you cannot audit your policy by reading config.

curl -sI https://example.org | grep -i content-security-policy

Contrib authors: POLICY_ALTER is how your module should declare its own CSP needs.

The practical takeaway from the previous slide.

Read the header, not the config form.

And if curl shows you two policies…

Both are enforced. The effective policy is their intersection, not their union — a resource must be allowed by every policy in force.

So if your CDN or web server sets one and Drupal sets another, adding a host in the Drupal admin UI changes nothing. The other policy still rejects it, and nothing in Drupal will tell you why.

Intersection, not union.

This is the one that makes people think the module is broken — they add a host, nothing changes, and there's no error anywhere to explain it.

Two things that will waste your afternoon

  • Caching. CSP is a response header, so Varnish and your CDN cache it like anything else. You change the config, test, see the old policy, and conclude the module is broken. Purge before you trust a test.
  • Config drift. Breakages are urgent and the policy is editable in the admin UI — a recipe for hotfixing prod and never exporting. A host live in prod's active config and absent from config/sync gets silently reverted by the next drush deploy, re-breaking the tag.

Both of these are from real debugging.

The caching one cost me most of a morning — I had a correct change in front of me and a stale response telling me it didn't work.

Put the policy in code

Both of those problems have the same root: the policy lives in a config form.

The CSP module lets modules and themes alter the policy in code, as the response is built.

Altering a site's policy — drupal.org

This is the recommendation I most want people to leave with.

An event subscriber

class EventsCspSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    return [CspEvents::POLICY_ALTER => 'onPolicyAlter'];
  }

  public function onPolicyAlter(PolicyAlterEvent $event): void {
    // DS-412: the events calendar embeds Eventbrite widgets.
    // Owned by Marketing. Remove when the calendar is retired.
    $event->getPolicy()->fallbackAwareAppendIfEnabled(
      'script-src', 'https://www.eventbrite.com'
    );
  }

}

Don't read the code out.

Point at the comment in the middle.

The important part is the comment

A host added in the admin UI is an undocumented string in a YAML file. Six months later nobody knows what it's for — and nobody dares delete it.

The same host added here is in version control, next to the reason, reviewed in a pull request, and deployed with the code that needs it.

It also can't drift. There's no active-config copy to diverge from config/sync.

This is the actual argument.

A host added through the admin UI is a string in a YAML file with no explanation attached. Six months later nobody knows what it's for, so nobody removes it — and the list only ever grows.

Put it here instead and it's in version control, next to the reason, and it went through review like anything else.

Which method?

  • fallbackAwareAppendIfEnabled() — the one you want almost always. Respects the fallback chain, and only acts if that directive (or its fallback) is actually enabled — so you can't accidentally switch a directive on and block everything else it governs.
  • appendDirective() — blunter. Adds regardless.
  • setDirective() — replaces the directive outright.
  • isReportOnly() — the event fires for the enforced and report-only policies. Check this if you need them to differ.

Themes can't register event subscribers, so they get hook_csp_policy_alter(Csp $policy, Response $response) instead. Modules should use the event.

fallbackAwareAppendIfEnabled is the safe default and it's what the docs recommend.

The others are there when you specifically need them.

Or attach it to the thing that needs it

$element['#attached']['csp']['img-src'] = ['https://cdn.example.com'];

// For inline code you genuinely can't remove:
$element['#attached']['csp_hash']['script-src-elem'] = [
  $hash => [Csp::POLICY_UNSAFE_INLINE, 'https://cdn.example.com'],
];

The source travels with the render element, so it's only in the policy on pages that actually use it — and it leaves the policy when the component does.

This is also the module-native answer to "I have inline JS I can't remove," alongside Attach Inline.

This scopes things better — the source is only in the policy on pages that actually use the component, and it leaves when the component does.

CSP and Google Tag Manager

Assets pulled in by analytics tools (GTM, GA) don't go through Drupal's back-end, so they aren't auto-added to your CSP — and get blocked the moment you enforce.

Options: nonce/hash the snippet (GTM supports a nonce), or have the Drupal Google Tag module emit the script as an external file.

<script src="/sites/default/files/google_tag/primary/google_tag.script.js?qgt931" defer></script>

That's the easy half — getting the snippet itself to load.

The module handles the loading half, and that's the easy part.

GTM is a hole in your change control

The snippet is one host. What it pulls is unbounded, and it changes without a deploy.

On a recent project, GTM loaded a Google Ads remarketing tag that beaconed to ad.doubleclick.net and got blocked on connect-src. Nobody on the dev team added that host — a marketer added a tag in GTM's UI.

No PR. No deploy. No notice.

Your CSP is now coupled to a config surface you don't control.

This part isn't really a technical problem.

Somebody outside the development team can change what your site loads, with no deploy and no notice. That's worth sitting with for a moment, especially in a government context.

…and 'strict-dynamic' doesn't save you here

It propagates trust for script loading only. It has no effect on connect-src, img-src, frame-src, or form-action.

Ad and analytics tags are mostly beacons — fetches, pixels, iframes. Precisely the set it doesn't touch.

'strict-dynamic' kills the script-src allow-list. It does not kill the allow-list.

You will still be hand-maintaining connect-src and img-src.

This corrects an assumption that's very reasonable to make.

It only covers script loading. Beacons, pixels and iframes are exactly the traffic it doesn't touch.

Where do violations go? Reporting

report-uri is deprecated. The current mechanism is report-to + the Reporting API.

Cover this even though it feels like an afterthought.

It's how you find out the policy is wrong before your users do.

report-to + Reporting-Endpoints

reporting-endpoints: csp-endpoint="https://example.com/report"
content-security-policy: default-src 'self'; report-to csp-endpoint;

You name an endpoint in a Reporting-Endpoints response header, then reference it from report-to. Firefox only enabled the Reporting API for CSP in v149 (early 2026), so for coverage send both report-to and legacy report-uri — newer browsers prefer the former. The Drupal CSP module supports reporting configuration.

And treat reports as diagnostics, not security telemetry: they're sampled, noisy (extensions!), and can leak URLs.

Send both directives for the moment, until support settles.

And treat what comes back as diagnostics rather than security telemetry — browser extensions generate a lot of noise in these reports.
