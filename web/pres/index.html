What is HSTS?

A response header that tells the browser to always connect to that domain over HTTPS.

strict-transport-security:
  max-age=31536000; includeSubDomains; preload

use https://hstspreload.org/ for validation and to register for preloading.

So what is HSTS? I'll keep this short, since you here to learn about CSP. But since HSTS was the other half of getting to an A grade, I'm covering it.

This tells the browser never to use plain http for this domain again (or for as long as the max-age is set).

Some other gotchyas though

It's improper to include this in a regular non-https response, even if you are redirecting to https

You shouldn't combine redirects for non-www and https. Redirect to https first, then issue a second redirect for www.

How can I set up HSTS?

In Drupal, the Security Kit module can do it. You can also set the header directly in PHP, or (better) at the web server / CDN layer.

Avoid slip when adding redirects

How to set it up.

Preference order is web server or CDN first, then a module (Security Kit).

It's a static header that never changes, so there's no real reason for PHP to be generating it on every request.

Really the biggest problem you run into with it, is you might add a redirect somewhere in say your htaccess, and forget to include the HSTS as a part of that

But don't worry, CISA will remind you in a month or so...

Warning

Once a site sends HSTS, if you ever let the certificate expire, no one will be able to reach the site.

The failure mode here is total, which is why it gets its own slide.

Browsers remember the header for as long as you told them to. So if the certificate lapses, nobody can reach the site, and there is no way to reach out and tell them otherwise. Start with a short max-age and raise it once you trust your renewal process.

What is CSP?

A policy that defines the acceptable sources a page is allowed to load resources from.

Yeah, but what does that mean?

An HTTP header that…

Defines what sources can be used on a web page.

content-security-policy: default-src 'self';

From here you add domains, nonces, hashes, protocols, and other options.

Same shape as HSTS — it's one header.

Everything else in this talk is detail about what goes after the colon.

Why do I need a Content Security Policy?

Move from what it is to why anybody bothers.

One example is enough here — I don't want to turn this into a scare session.

Basically, If someone successfully injects some code into your site, they might be able to exfiltrate user data. So PII, Credit Card info, admin session tokens.

British Airways breach (2018)

  • ~380,000 card payments skimmed by injected JavaScript (Magecart).
  • Initially fined £183m GDPR — reduced to £20m in 2020.

A restrictive connect-src could have blocked the POSTs to the attacker's domain.

Hacking is automated now — someone may just want to install a cryptominer. No site is too small.

This is the example I used in the original version of this presentation.

British airways, about 380k skimmed payments, resulting in significant fines.

But there have been more since, and it just seems that "Supply Chain" vulnerabilities are becoming more and more frequent.

Agentic AIs are pretty good at finding and exploiting vulnerabilities.

CSP is one of the strongest defense-in-depth controls against XSS and supply-chain script injection: even after malicious code lands on the page, the policy can stop it from executing or sending data away.

The attacker modified a JavaScript file served from BA's own site, so script-src 'self' alone would not have stopped it. The defensive opportunity here was restricting where that trusted script could send data.

A CSP is broken up into various "directives" that governs a type of resource.

There are quite a few. No need to memorize these.

Rules apply from specific to general

Browsers apply the most specific matching directive. If the specific one is absent, they fall back to the more general one.

Rules apply from specific to general

This is the mental model for the next several slides, so it's worth being clear before moving on.

Fallbacks stop at the first match

For a script attribute, the browser checks:

script-src-attr → script-src → default-src

The first directive present wins.
Sources are not merged.

No directive in the chain? CSP does not restrict that resource type.

Spec: fetch-directive fallback list

This is the whole fallback model: walk the chain and stop at the first directive that exists.

If none exists, that resource type is unrestricted. That is why default-src is an important safety net.

The fallback trap

frame-src → child-src → default-src

content-security-policy:
  child-src 'self' td.doubleclick.net;
  frame-src 'self';

The DoubleClick iframe is blocked.

frame-src exists, so the browser stops there. Fix it by putting the exception in frame-src.

Spec: fetch-directive fallback list

This is a real bug from a project I was on recently.

Someone allowed DoubleClick under the older, broader directive. Once frame-src was added, that allowance became invisible to frames because fallbacks are not merged.

The console reports an ordinary frame-src violation. It does not explain that child-src was ignored, because frame-src is present.

default-src isn't universal

It is a fallback for fetched resources, not every CSP rule.

default-src 'self';
form-action 'self';
base-uri 'self';
frame-ancestors 'self';

Set the last three explicitly. Without form-action, an injected form may still submit off-site.

Spec: default-src

This is the one caveat to the fallback model worth keeping: default-src only participates in fetch-directive chains.

A policy can look locked down and still allow a form to post elsewhere unless form-action is explicit.

object-src 'none'

<object> and <embed> can execute scripts.

script-src does not govern them.

object-src 'none';

Flash may be gone, but this directive still lives on. A same-origin HTML or SVG upload is still a realistic way for somebody to put an executable document on your origin.

object-src falls back to default-src

Key features in CSP

Key features in CSP.

'unsafe-inline'

content-security-policy: script-src 'self' 'unsafe-inline';

Allows inline scripts/styles. i.e. anything inside a <script> tag, or "onclick" handler.

Weak — but still better than no CSP at all as a starting point.

This is where most people start, and it's a reasonable first step, since there is a lot of legacy code added inline.

But it's very permissive, and ultimately should be avoided where possible.

Hashes

content-security-policy: script-src 'sha256-B2yPHKaXnvFWtRChIbabYmUBFZdVfKKXHbWtWidDVF8='

Allow-list a specific inline script or style by the base64-encoded SHA hash of its contents.

Note: adding any hash or nonce to script-src makes the browser ignore 'unsafe-inline' (a feature, not a bug).

MDN: script-src

Generate a hash of the contents of some inline code, and use that in the header to allow it to run.

The detail worth pointing at is the last line. Adding any hash or nonce switches unsafe-inline off, whether you meant to or not.

The hash gotcha

Plain hashes (and nonces) only apply to elements — <script> / <style> blocks.

They do not cover inline event handlers (onclick=) or inline style="" attributes…

Reference

This is the one that costs people an afternoon.

Hashes cover elements. They don't cover attributes, and the error message doesn't make that obvious.

'unsafe-hashes'

content-security-policy: script-src 'unsafe-hashes' 'sha256-...';

The CSP Level 3 keyword that lets a hash match an inline event handler or style attribute — the gap from the previous slide.

Still "unsafe" (less so than 'unsafe-inline'). The better fix is to remove inline handlers/attribute styles entirely.

content-security-policy.com/unsafe-hashes

This is the escape hatch for the previous slide.

Better than unsafe-inline, still not something to be happy about. Removing the inline handler is the actual fix.

Nonces

<script nonce="ABC123">…</script>
content-security-policy: script-src 'nonce-ABC123'

Allow-list inline code by an arbitrary, server-generated string. Generate a fresh nonce on every request.

MDN: script-src

A random value, regenerated on every request, matched between the header and the tag.

If you are thinking what I'm thinking, this is problematic for serving content from cache.

Don't use static nonces.

A nonce that never changes is just a password the attacker can read — it defeats the purpose.

Don't hardcode, or use the same nonce over and over, that defeats the whole point of them.

Hashes and nonces are tedious to manage by hand…

These are tedious to manage by hand.

…and easy to get wrong. (I forgot to set default-src here.)

Rule of thumb

  • Nonces when you can generate markup dynamically. Works with Dynamic Page Cache.
  • Hashes when the content is static / cached and you can't inject a per-request nonce.

Browser support for newer CSP features still varies.

Granular directive support is now broad, but not universal.

A weak CSP (lots of 'unsafe-inline' / wildcards) can still let attacks through —

Worth being honest about what it doesn't do.

A weak policy gives you the header and the passing grade without much of the protection.

So to really know what a CSP holds, Read the header as it is on the page.

And if curl shows you two policies…

Both are enforced. The effective policy is their intersection, not their union — a resource must be allowed by every policy in force.

*Can happen if your CDN and Drupal both set a CSP.

If you end up with multiple policies, Intersection, not union. I see this when a Client's IT team sets it in the WAF, but you also have Drupal Dynamically generating one as well.

The browser enforces all of them, independently.

An event subscriber

class EventsCspSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    return [CspEvents::POLICY_ALTER => 'onPolicyAlter'];
  }

  public function onPolicyAlter(PolicyAlterEvent $event): void {
    // ABC-123: the events calendar embeds Eventbrite widgets.
    // Owned by Marketing. Remove when the calendar is retired.
    $event->getPolicy()->fallbackAwareAppendIfEnabled(
      'script-src', 'https://www.eventbrite.com'
    );
  }

}

I'm pushing to define Additional CSP rules like this, in an event subscriber where you can add inline code comments explaining why a specific resource is used.

The important part is the comment

A host added in the admin UI is an undocumented string in a YAML file. Six months later nobody knows what it's for — and nobody dares delete it.

The same host added here is in version control, next to the reason, reviewed in a pull request, and deployed with the code that needs it.

It also can't drift. There's no active-config copy to diverge from config/sync.

fallbackAwareAppendIfEnabled()

The safe default for adding a source.

$policy->fallbackAwareAppendIfEnabled(
  'script-src', 'https://www.eventbrite.com'
);
  1. Directive exists? Append to it.
  2. Fallback exists? Copy the nearest, then append.
  3. Neither exists? Do nothing.

This mouthful of a method is the safest to use here. Remember that fall back trap I talked about earlier?

This avoids creating a narrower directive containing only the new source, which would accidentally block everything the fallback had allowed.

The other policy methods

  • appendDirective() — append directly; create the directive if needed.
  • setDirective() — replace the directive outright.
  • isReportOnly() — distinguish the enforced and report-only policy events.

Themes use hook_csp_policy_alter(). Modules should subscribe to CspEvents::POLICY_ALTER.

These are the other methods available. But just use that safe one.

Or attach it to the thing that needs it

$element['#attached']['csp']['img-src'] = ['https://cdn.example.com'];

// For inline code you genuinely can't remove:
$element['#attached']['csp_hash']['script-src-elem'] = [
  $hash => [Csp::POLICY_UNSAFE_INLINE, 'https://cdn.example.com'],
];

The source travels with the render element, so it's only in the policy on pages that actually use it — and it leaves the policy when the component does.

This is also the module-native answer to "I have inline JS I can't remove," alongside Attach Inline.

or attach it.

This scopes things better — the source is only in the policy on pages that actually use the component, and it leaves when the component does.
